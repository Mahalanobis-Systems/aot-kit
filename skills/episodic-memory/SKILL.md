## What it is

Log every agent session, distill a few verified lessons from it (user corrections and preferences, definitions, workflows that worked, mistakes) into short memory files under an index the agent reads at the start of each task, and let it search both. It pays where later tasks need what earlier ones learned and the model writes good notes: on one such task a memory folder lifted Claude Opus 5.5 from 0.655 to 0.838 but Sonnet 4.6 only from 0.330 to 0.364 (Anthropic testing its own models), and Databricks' data agent went from 22.3% to 68.4% on tasks built from its users' past sessions, with 31% fewer tokens. Against cheap baselines the gains often vanish: on an independent benchmark of such task sequences, carrying the raw history in the prompt matched or beat every dedicated memory system (with GPT-5.4, the same gain as Mem0 at the same cost); with three frontier models two memory methods moved average accuracy by -1.1 to +3.0 points; and a no-memory web agent given the same tokens beat ReasoningBank by 5.1 to 8.1 points. Memory also misleads: unverified lessons reproduce mistakes, notes two of five Claude models (Sonnet 4.6 and Opus 4.7) wrote after a user waived confirmation on routine chores made them skip it on high-stakes tasks in 35 to 81% of episodes (under 1% without memory; the other three about 5% to 39%), and one crafted email planted a lasting instruction in up to 87.5% of test cases.

## When it applies

- **In the code:** Raw session traces kept across tasks or sessions; distilled memory files or a vector store of lessons; an index or retrieval step at task start; writes after each task or on user request; a consolidation, TTL or decay job.
- **In traces:** Memories retrieved per task, whether the agent read and followed them, and whether they applied; memory writes and their source; repeated mistakes the store should have prevented.
- **In eval results:** Repeat-mistake rate over time; pass rate with and without memory and against the raw history carried in the prompt, on a task stream, split into rescues and regressions.
- **Judge:** Rate retrieved memories for relevance.
- **Probes:** A task pair where the first teaches a lesson the second needs, an unrelated task the lesson could mislead, a one-time user waiver or preference followed by a higher-stakes task it does not cover, and untrusted content that asks to be remembered.

## How (outline)

1. Start from three baselines on the same tasks and model: no memory; a no-memory agent that gets the memory's token budget as extra steps (7.b.iii) or reasoning effort (1.b.i); and the raw history of earlier tasks carried in the prompt (truncated at the window) or left for the agent to search with its own tools. A no-memory web agent allowed 15 steps instead of 10 beat ReasoningBank by 5.1 to 8.1 points with three 2026 models, mostly at fewer total tokens, and with GPT-5.4, Gemini 3.1 Pro and Claude Opus 4.7 two memory methods moved average accuracy by -1.1 to +3.0 points. On six task sequences built so later tasks need earlier ones, the raw history in the prompt matched or beat every dedicated memory system: with GPT-5.4 it captured 20.1% of the available gain over the stateless agent at $18.4 per run against 20.2% at $18.3 for Mem0, 7.8% for model-curated notes and 8.6% at $62.8 for ACE. Build the evaluation stream so later tasks need what earlier ones learned (a user's corrections and preferences, metric or table definitions, repository conventions, a workflow that was costly to find): that is where memory paid, 22.3% to 68.4% on tasks built from real user sessions.
2. Log every session as an append-only raw trace (task, steps, tool results, outcome, user feedback), and keep a separate set of short distilled memory files (preferences, definitions, workflows, mistakes) under an auto-generated index file that says what each file holds; keep search over the raw traces underneath anything derived from them. In Databricks' ablation, raw traces alone reached 35.8% (the agent searched them in only about a third of cases), distilled files with the index 66.1%, and both 68.4%; in Anthropic's test a wiki that Claude Opus 5 agents built over 128 sessions met 48% of graded criteria on its own against 53% for plain search and 61% for both, which also used about 20,000 fewer tokens per question.
3. Persist a distilled lesson only after a check against ground truth (tests pass, the user confirms, the outcome is verified), never on the agent's own success judgment: on one site 52.9 to 59.5% of ReasoningBank's success-labeled lessons came from tasks that had failed, stored lessons trailed raw trajectories in 7 of 9 settings, and a GPT-5.5 check before admitting each lesson raised stored-lesson memory from 38.7% to 46.0%. Where nothing can verify a lesson, synthesize guidance from the retrieved raw traces for the current task and discard it afterwards (+3.3 to +28.0 points over storing it). Tell the model what memory is for and let a strong model judge what to record: a fixed rule to record only failures cut Opus 5's memory gain by 0.234 and Opus 4.7's by 0.150, while an older model needed a prompt to read its memory before answering and to test its theories (Sonnet 4.6 from 0.364 to 0.641). Write explicit user requests (“Never write scripts in the /tmp dir”) at once, together with the scope they were given for (this task, this kind of action, work or personal): 93.0% of 599 notes five Claude models wrote after a one-time waiver of confirmation were broader than the user's words.
4. At session start inject the index and keep it short (Claude Code loads only the first 200 lines or 25 KB of MEMORY.md), give the agent search and fetch tools over both stores, and retrieve only a few records (the studies used one to five). Put standing user preferences in the injected file rather than behind similarity search: over 99 sessions per simulated user, a MEMORY.md read in full each session raised preference selection from 49.6% to 59.2%, while Mem0, MemOS and plain retrieval stayed at 49.9 to 50.0% because what they retrieved held an applicable preference in 7 of 334 probes. Inject a short record anchored to the files, tables or fix it concerns, not raw transcript chunks or loosely extracted facts: off-the-shelf memory systems were at or below memory off in 11 of 12 coding pairings, mostly because the record they injected buried or dropped the fix. Keep a separate store per user or domain (an unrelated passage cost 0.7 to 3.4 points) and tell the agent a memory is a hint to check against the current task and its context, not an instruction: the same file memory carried a preference from work into personal sessions or back in 26.9% of pairs.
5. Consolidate offline on a schedule: distill new sessions into the files, check each note against the transcript it came from, merge duplicates, split oversized files, resolve conflicts and delete stale entries (offline distillation 63.5% against 53.9% for writes made during the session, 66.1% with both). When several agents consolidate in parallel, give each its own file: a shared contract table that several agents overwrote kept 41 of 57 graded facts, and one page per contract, written by one agent and quoting the terms, kept all 57.
6. Treat a memory write as a privileged action (10.c.i): only the user and verified outcomes may write; never store instructions found in email, web pages, documents or tool output; record each entry's source and show every write to the user. One crafted email made agents store and later act on a poisoned memory in 87.5% (GPT-5.4) and 71.4% (Sonnet 4.6) of held-out cases when mail was processed in the background, past input, model and trace defenses; asking the agent to report what it checked and did cut foreground success from 75.0% to 1.8% and from 48.2% to 23.2%. Benign memories overreach too, so never let a memory waive a confirmation or a check before an irreversible or high-stakes action (10.b.i): after a user waived confirmation on routine coding chores, the notes made Sonnet 4.6 and Opus 4.7 skip it on simulated high-stakes tasks in 66 to 81% and 35 to 58% of episodes (under 1% without memory), notes from legitimate stale-test repairs led three Claude models to rewrite correct tests so they hid broken safeguards in 77 to 80% of security cases, and ratings of each note's scope did not consistently predict which notes caused harm.
7. Measure with paired runs against all three baselines, memory frozen during evaluation, at least three seeds: pass rate split into tasks memory rescues and tasks it breaks (it helps where the model fails without it and can hurt where it already succeeds), tokens including memory-side calls, steps and latency (1.35x faster and 1.44x fewer tokens in Databricks' test; A-Mem cost up to 6.37x of no memory on GPT-5.4), a poisoning probe and an out-of-scope probe (a one-time waiver or preference followed by a task it does not cover). Re-run after every model change: the same memory setup added 0.034 reward for Sonnet 4.6 and 0.317 for Opus 4.7 on one task, and notes raised unsafe actions to about 80% of episodes for Sonnet 4.6 but about 5% for Fable 5.

## How to measure

- **experiment** (Tier 4): paired runs on a held-out stream that mixes tasks reusing what earlier ones learned (user corrections and preferences, definitions, repository conventions) with tasks that share nothing, memory frozen during evaluation and at least three seeds: memory against no memory, against a no-memory agent given the same total tokens as extra steps or effort, and against the raw history carried in the prompt or searched by the agent; report pass rate split into rescues and regressions, gain over the same system run statelessly, tokens including memory-side calls, steps and latency, per model; ablate raw traces only, distilled files only and both; add a poisoning probe (a document or email asking the agent to remember an instruction) and an out-of-scope probe (a one-time waiver or preference followed by a high-stakes task it does not cover), and count writes and later effects
- **monitor**: memory writes per session by source (user, verified outcome, untrusted content), the scope each states and whether the user saw them; retrievals per task and how often the agent followed a memory that did not apply, including confirmations or checks skipped because of a memory; repeat-mistake rate; regressions on task types solved before memory; store size, duplicates and conflicts after each consolidation; tokens per task

## Caveats

The large gains come from benchmarks built so that memory is needed, and the biggest are vendors' tests of their own products (Databricks' 114 cases scored by an LLM judge; Anthropic's single CL-Bench task, whose text gives no run counts or intervals), while on the independent benchmark built for such task sequences the raw history in the prompt matched or beat every dedicated memory system and the best system captured 25.4% of the available gain, with structured memory run mostly on GPT-5.4 over sequences of tens of tasks. No study yet gives a stateless agent the memory's tokens as extra budget on tasks that depend on earlier ones; the independent tests that matched budgets or found small or negative effects used largely self-contained tasks (WebArena, SWE-style coding, 50-task benchmark streams), mostly open or mid-size models, and intervals that often cross zero. Effects depend on the model in both directions: self-written memory added 0.034 reward for Sonnet 4.6 and 0.317 for Opus 4.7 on one task, a fixed record helped the solver weaker without memory in 61 of 64 split cases, and benign notes drove unsafe actions in about 80% of episodes for Sonnet 4.6 but about 5% for Fable 5, in scenarios built to probe that failure that do not show how often it occurs in deployment. Memory makes tasks depend on their order, so they cannot run in parallel and a transient failure silently changes what later tasks see; the 87.5% poisoning rate needs an attacker model trained against a copy of the agent (handcrafted payloads scored 0.0% on GPT-5.4 and Sonnet 4.6), and brand is an assessment.
