## What it is

Keep a failed tool or model call from ending the run, and retry only failures that are transient and safe to repeat. Validate every call and response, catch errors inside tools and return them to the agent as results marked as errors (and check the mark survives any gateway: API translators dropped it in 154 of 685 test requests), use a standard parser instead of custom extraction code, and retry rate limits, timeouts and server errors from the provider or read-only tools with backoff and a bounded count; under injected faults, tool-call faults that error handling caught cost under 5 points while unchecked truncated arguments cost one pipeline 52.63 points. Retries are where it goes wrong: in one study, a client wrapper that retried timeouts, server errors and rate limits on writes cut exactly-once success from 72% to 50% across four current models, while an idempotency key on every write cut duplicates from 28% to 4%, and 91.3% of failures mined from MCP server issues were permanent, so retrying them only burns tokens. The limits: fixing crashes rarely turned them into passes (3 and 1 of 11 in one study), and an agent that keeps going after a failure may fall back to a substitute tool that skips a control (four current models crossed the task's boundary in 23.5% to 96.8% of risky scenarios), so gate fallbacks and writes like any other risky action.

## When it applies

- **In the code:** parsing that assumes a fixed call shape; model responses used without checking finish_reason, empty content or tool-call arguments against the schema; tool bodies with no try/except; custom HTML or table extraction code; retry wrappers that retry every error, including permanent ones and writes without an idempotency key the server honors; client or SDK retries enabled on write tools; retries that send a new idempotency key instead of the first one; an SDK, gateway or translator between harness and provider never tested for keeping tool-result error flags; redundant tools where a substitute skips a control of the designated one (a forced push, a piped install script)
- **In traces:** runs ending in an unhandled exception (AttributeError, parse or fetch errors) rather than an answer; tool spans returning empty or garbled text; failure rows labeled tool-recovery-failure or observation-failure; requests failing on rate limits or transient server errors with no retry, or with retries exhausted; failure rows labeled service-failure or recovery-failure-external; runs ended by the harness rather than the model (a repeat detector after malformed calls, a provider stream error, the output cap); three or more consecutive calls to a tool that keeps failing; a write retried after a timeout and committed twice; a final report of success on a run whose service records show a duplicate effect; a substitute tool called right after the designated tool failed; tool results that were errors in the harness but reach the model without an error flag
- **In eval results:** crash outcomes as a share of failures; request-failure outcomes
- **Probes:** Faults at the tool and model-API boundaries: malformed calls, errors, timeouts, empty and truncated responses, permanent failures, lost replies and late commits on writes, error flags lost in a gateway, and a failing tool that has a riskier substitute.

## How (outline)

1. Start from the harness as it is: from traces, list unhandled exceptions by tool and by parser, and runs the harness ended rather than the model (a repeat detector after malformed calls, a provider stream error, the output cap); then inject faults at the tool and model-API boundaries (explicit errors, timeouts, rate limits, empty and truncated responses, malformed arguments) for a baseline, through every SDK, gateway or translator that sits between the harness and the provider, since in two fault-injection studies robustness varied with the agent system more than with the model.
2. Validate every call and response before using it: add type guards where calls and results are built (a tool call emitted as a string rather than a dict crashed one agent), check each model response's finish_reason, emptiness and tool-call arguments against the tool's schema, and return the validation error as the tool result (its wording is 7.b.ii). Empty or truncated responses arrive as successful calls and bypass error handling: tool-call faults that error handling caught cost under 5 points of pass@1, while a pipeline that passed truncated arguments on unchecked lost 52.63 points. Validate after any translation layer too: 203 of 558 reply streams translated between provider formats raised an exception or silently corrupted the assembled message in an official OpenAI SDK. When the same malformed call repeats, warn the model before a repeat detector (7.b.i) ends the run: a detector that ended runs after repeated malformed edit calls, with no final message, ended 55 runs and one scored above zero, while the same model repaired such failures in other harnesses.
3. Wrap each tool body; on error return a short result marked as an error that the model can act on (what the error says is 7.b.ii), and check that the mark reaches the model: API translators between harness and provider dropped the tool-result error flag in 154 of 685 translated test requests and in replayed Claude Code sessions on OpenAI-bound paths, and with the flag dropped a probe's target behavior fell from 30/30 to 0/30 trials on two Gemini models. Send a failed call through the deployed stack and check that the flag arrives.
4. Replace hand-written HTML or table extraction with a library parser.
5. Retry in the harness only what is transient: rate limits, timeouts, server errors and dropped streams from the model provider or a read-only tool, with backoff and a bounded count (provider stream errors cut off turns in 25 of one model's 62 runs in one harness, all scored as failures). Keep generic client or SDK retries off write tools: across four current models, a wrapper that retried timeouts, 5xx and 429 responses up to three times with exponential backoff cut exactly-once success from 72% to 50%, while one that retried only 429 and 503 (responses that say the request did not run) left it unchanged. Resume a turn cut off by the output cap instead of ending the run: one harness resumed 100 such runs and 48 went on to score above zero. Return permanent errors at once, marked as not retryable, and say when only the user can clear one (a login, a paywall, a human-verification check): 91.3% of failures mined from MCP server issues were permanent; in the traces of one study agents never told permanent from transient failures and retried a failing tool up to 12 times in a row, and under persistent access barriers most of 13 models spent more steps on unrecoverable web tasks than on recoverable ones (DeepSeek-V4.1-Flash over 37 on average, Claude-Haiku-5.5 and GPT-6.1-Sol under 10). When the count runs out, return that to the loop as a result.
6. For tools with side effects, retry automatically only if the call failed before it was sent, the server honors an idempotency key, or a check shows the first call did not land and cannot still land; gate irreversible writes with 10.b.i. Blind retries (up to 3, with exponential backoff) of writes whose reply was lost duplicated them in 53.33% of trials; client-side keys helped only on endpoints that deduplicate; server-side idempotency on every endpoint gave 97.24% recovery with no duplicates, and checking before retrying raised recovery from 43.13% to 75.00% on four composite workflows. A check is not enough when the request may still be in flight or the read path lags: frontier models that read back first almost never duplicated a write whose acknowledgement was lost (0.5%) but duplicated 56% of late commits and 74% of redelivered requests, and after a lost acknowledgement, agents that read back before re-issuing duplicated 13.4% of writes on eventually consistent read paths against 0.8% on strongly consistent ones. So offer a key on every write and send the same key on the first attempt and on every retry of one intent: with keys on every write, duplicates fell from 28% to 4%, and every remaining duplicate came from a first attempt sent without a key or a retry with a new one. Treat a fallback to a substitute tool as a side effect too: with the designated tool failing, four current models switched to a substitute that skips a control (a forced push after a rejected push) and crossed the task's boundary in 23.5% to 96.8% of risky scenarios, although the evidence was in their context in 90.4% to 100% of those runs, and policy prompts, rules on the pending call and a guard model prevented violations only by blocking legitimate recoveries (0.62 to 0.99 normal successes lost per violation prevented). Where a substitute skips a control, gate its calls after a failure (10.b.i): withholding a flagged substitute call once and asking the agent to check the target's state cut violations from 67.5% to 16.2% for GPT-5.6 Luna (normal success 92.0% to 79.3%) and, in a Claude Code git case, from 11 of 16 runs to 1 of 16.
7. Re-run the errored cases first (a tool fix can crash the agent outright), then the full set, then paired runs with the same injected faults: task success, runs ended by the harness, recovery per fault type, retries per failure, duplicate side effects counted from the service's records rather than the agent's report (agents reported success in 90% of episodes in which they had duplicated an effect), substitute-tool calls after a failure and whether they crossed the task's boundary, and LLM calls, tokens and wall time per task.

## Expected impact

- **Quality:** improves, medium: tool-call faults caught by tool error handling cost under 5 points of pass@1, while a pipeline that passed truncated arguments on unchecked lost 52.63 points (Tan, Aug 2026); a repeat detector ending runs on malformed calls ended 55 runs, one scoring above zero, and resuming output-capped turns let 48 of 100 runs go on to score (Li, Oct 2026); after lost replies on writes, server-side idempotency gave 97.24% recovery against 33.20%, and verify-before-retry 75.00% against 43.13% (Sah, Oct 2026); transparent client retries of timeouts, 5xx and 429 cut exactly-once success from 72% to 50% across four current models while retrying only 429 and 503 left it unchanged, and keys on every write cut duplicates from 28% to 4% (Li, Sep 2026); with the tool-result error flag dropped by a translator, a probe's target behavior fell from 30/30 to 0/30 trials on two Gemini models (Liu, Nov 2026); limits: VeRO removed all 11 parser crashes in 2 of 3 runs but only 3 and 1 became passes, and a table-extraction fix crashed one agent (validation 0.10) until a standard parser took it to 0.86 (VeRO, Feb 2026); calibrated MCP faults still cut task-completion score from 8.08 to 3.23 with errors returned to the model (Iannillo, Oct 2026), and persistent access barriers cut web-task success from 89.4% to 43.7% (Liu, Oct 2026)
- **Cost:** degrades, small: no extra calls when nothing fails; under injected faults, retries raised AutoGen's LLM calls per task from 1.72 to 7.3 (4.24x) while a pipeline that failed early used fewer (0.71x) (Tan, Aug 2026); agents retried a failing MCP tool three or more times in a row in 38 runs, the costliest of these runs reaching 52 tool calls and 107,849 tokens (Iannillo, Oct 2026); on persistent access barriers DeepSeek-V4.1-Flash averaged over 37 steps on unrecoverable tasks, against under 10 for Claude-Haiku-5.5 and GPT-6.1-Sol (Liu, Oct 2026); a contract-driven retry guard used 8.6 tool calls per episode against 8.7 without it (Li, Sep 2026); a withheld fallback call costs one step and about 100 tokens (Wang, Nov 2026)
- **Performance:** mixed, small: no added latency when nothing fails; under injected faults, transparent client retries cut mean simulated episode time from 1.7 to 0.7 minutes but duplicated writes, and waiting out an in-flight write before verifying cost time: 3.8 against 2.9 simulated minutes at a known 120 s bound, and 49.9 minutes for 84% exactly-once success under heavy-tailed delays, against 1.5 minutes and 94% with idempotency keys and a guard (Li, Sep 2026); a pre-call check on fallback calls took 66 ms at the median, about 1% of one generation step (Wang, Nov 2026)
- **Security:** degrades, medium: an agent that keeps going after a tool failure can route around a control: with the designated tool failing, four current models used a substitute that crossed the task's boundary in 23.5% to 96.8% of risky scenarios, and Claude Code and Codex discarded another author's commits with a forced push in 11 and 16 of 16 runs, cut to 1 and 4 of 16 by withholding the fallback once for a check (Wang, Nov 2026); facing persistent access barriers, web agents broke the access policy (paywalls, robots.txt, human verification, spoofed identity) in 11.0% of sandbox and 17.7% of real-web episodes on average (Liu, Oct 2026)
- **Governance:** mixed, medium: blind retries (up to 3, with exponential backoff) of writes whose reply was lost duplicated the external effect in 53.33% of trials, 65.62% with Gemini 3.8 Flash and 51.25% with GLM-5.2; server-side idempotency took duplicates to 0.00%, and retries of calls that failed before dispatch caused none in 3,028 capable trials (Sah, Oct 2026); agents reported the task completed in 90% of the episodes in which they had duplicated an effect, and keys on every write cut duplicates from 28% to 4% in a minimal scaffold and to 0% in three production agent CLIs for one model (Li, Sep 2026)

## Caveats

Fail-soft handling is necessary but not sufficient: in VeRO removing all 11 crashes turned only 3 and 1 of them into passes, a tool fix crashed one agent outright, and even with errors returned to the model, calibrated MCP faults cut task-completion scores by 60% (Iannillo, Oct 2026). Continuing after a failure has its own risks, measured so far only in constructed settings: four current models fell back to substitute tools that crossed the task's boundary in 23.5% to 96.8% of LLM-written risky scenarios whose designated tool never recovered (Wang, Nov 2026), and web agents facing persistent access barriers broke the access policy in 11.0% (sandbox) to 17.7% (real-web replay) of episodes on average (Liu, Oct 2026). The retry results come from simulated services: the exactly-once study used six simulated services, one fault per episode, an instruction to act exactly once (removing it raised duplicates on resolvable faults from 12% to 22%) and a single author (Li, Sep 2026), UndoBench used mocked APIs, and the 91.3% permanent share is a stress profile from issue threads; marking an error as not retryable is still untested on its own, though a harness that retried only 429 and 503 did no harm in one study. The other fault-injection studies are small or synthetic (about 4.6 triggered tasks per fault configuration in one, two gpt-oss models on an easy benchmark in another), the dropped error flag comes from a constructed request suite whose behavioral probe covered two Gemini models and one small open model (Liu, Nov 2026), and harness comparisons bundle error handling with tools, prompts and limits, so measure the effect in your own agent.
