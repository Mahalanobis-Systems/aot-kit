## What it is

Show the agent every failed action as a marked error it can read, with the next step it can take, instead of hiding it, and collapse the error once it is fixed. Return the call, the cause and a capped trace as an error result rather than swallowing the exception, retrying silently, returning an empty or plausible-looking result or deleting the failed attempt. On one benchmark agents recovered from explicit failures 37 points more often than from silent ones across nine models, a note naming the recovery tools on silently failed results raised completion from 10.9% to 28.1% on four current open-weight models, and one model almost never misreported a failure marked status:error (at most 1.2%) but answered dishonestly in up to 45.3% of failures returned as status:ok. The limits: deleting the failed exchange did only 1.9-3.8 points worse than keeping it across 13 open models, in 135M-1.7B models the verbatim failed call made exact repeats more likely (though deleting it was worse), a model's own unflagged mistakes raise its later error rate, on HumanEval restarting fresh after 2-3 failed fixes beat continuing, and instructions planted in third-party error text can steer the agent; so keep the diagnosis and the next step, cap it, strip instructions from third-party errors, and don't let failures pile up.

## When it applies

- **In the code:** Exceptions swallowed or retried silently; failures returned as empty, null or default results with a success status; a generic "operation failed" in place of the cause; failed attempts deleted before a retry; harness notes that rewrite earlier messages instead of appending; full stack traces or test logs passed untruncated; third-party error text passed through with steps the agent cannot take (a terminal command, a config change, a web page) or with instructions to act (send, forward, run).
- **In traces:** Errors absent from the next model input or not marked as errors; exact repeats of a call that already failed; runs of failed fixes of the same error; agents stopping after error text that asks for a step they cannot take; final answers asserting a value after a tool returned nothing usable; actions taken because an error message asked for them; error observations thousands of lines long.
- **In eval results:** Recovery rate per injected failure, repeat rate of failed calls and the rate of final answers asserting values a failed tool did not return, alongside task success.
- **Probes:** A tool that fails deterministically on first use.

## How (outline)

1. Start from the harness as it is and find every place a failure is hidden from the model: exceptions swallowed, silent retries, a failed attempt deleted before the retry, a generic "operation failed" in place of the cause, or an empty, null or default result returned with a success status. Inject a few failures (a tool that fails on first use, a silent wrong result, a third-party error message, one that embeds an instruction to act) and record recovery, repeated failed calls and what the final answer claims.
2. Return every failed action to the model in the next turn as a tool result marked as an error in the envelope (is_error, isError or status: error): the call (tool and arguments), the error type, the cause message and the exit code. Never turn a failure into an empty or plausible-looking result: on one benchmark agents recovered from silent failures 37 points less often than from explicit ones, and in one study a model answered dishonestly in up to 45.3% of failures returned as status ok with an unusable value, against at most 1.2% when the tool returned status error. Where a tool can fail silently, check its results against cheap output contracts (required fields, types, allowed values, sign, simple totals) and, on a violation, keep the result and attach a short note naming the violated property and the tools that can recover it: on four current open-weight models that raised completion under silent failures from 10.9% to 28.1%. Keeping the loop alive when a tool raises is 2.b.i.
3. Cap what goes in: keep the exception type and message, the frames in the agent's own code and the last lines of output; write the full trace or log to a file and give the path (2.c.i); make test and lint runs print a few lines, with ERROR and the reason on one line. Write the errors you own so they name the next step (the call to repeat, the value to change, the tool to switch to): in the contract-note study the list of recovery tools carried the gain, while more diagnostic detail added nothing detectable. Treat third-party error text as untrusted: strip sentences that ask for steps the agent cannot take (a terminal command, a config change, a web page; in one study a one-sentence filter prompt raised recovery on expired credentials from 45% to 82%) and any instruction to act (send, forward, run, authenticate), and require approval for side-effecting actions an error message asks for (10.c.i, 10.b.i): in one small red-team study all four frontier models tested followed an exfiltration instruction planted in a tool error once it was reworded, while two coding CLIs with approval gates blocked it.
4. Keep the failed exchange and append, don't rewrite: under greedy decoding, retrying from a context with the failure deleted repeated most in small models, and across 13 open models (3B-70B) deleting the failed call and its error did 1.9 to 3.8 points worse than keeping it (both followed by the same note), while deleting it and restating it in the earlier user message broke stopping in Llama models (Llama-3.3-70B stopped after unrecoverable errors in 2% of cases, against 95% with the history untouched). To steer the next action, add a short harness note after the kept failure as a new turn, with what failed, its kind and the next step: on real coding-agent histories that raised correct next actions by 34.4 points over the tool error alone, and it beat the same sentence inside the tool result in 10 of 13 models. Put only facts the harness knows in that note (tool, arguments, error kind, next step), not third-party error prose: the study's authors caution, untested, that tool text restated in a user turn gains authority. If a small model re-emits a failed call verbatim, refuse exact repeats (7.b.i), or replace the verbatim call string with a short description of what failed while keeping the error and its diagnosis (it cut repeats in 135M-1.7B models; check stopping per model family if you do).
5. Drop errors once they are resolved: when a later call succeeds or the tests pass, collapse the old error observation to a one-line stub, keep only the first of a run of identical format errors, and carry only unresolved errors through compaction (5.a.i). Don't let failures pile up: after 2-3 failed fixes of the same error, restart from the original task (optionally with a one-line note of what failed) or hand off, since non-thinking models make more mistakes as their own uncorrected errors accumulate in context.
6. Measure with paired runs on the same tasks and injected failures, the harness as is against errors kept, marked, capped and dropped once resolved (and, for silent failures, with contract notes), per model: task success, recovery rate per injected failure by type (the agent's own call, credentials, permissions, rate limits, silent wrong results), exact and canonical repeat rate of failed calls, runs ending in a loop, final answers that assert a value a failed call did not return, compliance with instructions planted in error text, steps and tokens. Include fault-free runs (a contract note on a correct result harmed as often as it rescued in one study), and re-run after a model change: the repetition effect shrank with model size, the effect of deleting the failed exchange differed by model family, and thinking models did not self-condition.

## How to measure

- **experiment** (Tier 2): paired runs on a fixed task set with failures injected at fixed steps (a tool that fails deterministically on first use, a silent failure that returns a plausible but wrong value, a third-party error that names a step the agent cannot take, and one that embeds an instruction to act): the harness as is against failures returned as marked error results with capped traces and collapsed once resolved, with contract notes on silent failures, and optionally with the failed exchange deleted or with a harness note appended as a new turn; per model: task success, recovery rate per injected failure, exact and canonical repeat rate of failed calls, runs ending in a loop, final answers asserting a value the tool did not return, compliance with the planted instruction, steps and tokens; include fault-free runs to count harms
- **monitor**: in production traces: the share of failed tool calls whose error text reaches the next model input marked as an error; results returned with a success status but an empty, null, redacted or truncated value; exact repeats of a call that already failed; consecutive failed attempts on the same error; the size of error observations; contract notes fired per tool and how often they fire on results that were correct; final answers that assert a value after a failed call; actions taken because an error message asked for them; and recovery after errors by failure type (the agent's own call against credentials, permissions and rate limits)

## Expected impact

- **Quality:** mixed, medium: recovery from silent failures 37.15 points below explicit errors, averaged over nine models (Zhu, Jun 2026); a contract note naming recovery tools on silently failed results 28.1% vs 10.9% completion on four current open-weight models and +14.0 and +12.0 points on τ-bench retail, no net effect where most runs completed anyway (Panthi, Aug 2026); deleting the failed exchange 1.9-3.8 points below keeping it across 13 open models, a new-turn note with the next step +34.4 points on real coding-agent histories and +14.2 and +10.5 points on ToolMaze explicit errors, no gain on Loud/Quiet (Woo, Nov 2026); lint errors shown with the bad edit rejected 18.0% vs 15.0% on SWE-bench Lite (Yang, May 2024); in 135M-1.7B models a kept verbatim failed call raised repeat probability from 0.06 to 0.54, while deleting it raised exact repeats from 31% to 80% (Gumaan, Aug 2026); wrong answers in a model's own history lowered later accuracy in non-thinking models of every size tested (Sinha, Sep 2025); fresh starts after 2-3 failed debug attempts beat continuing, e.g. 72.56% to 82.82% (Adnan, Jun 2025); a developer-facing step in the error text cut recovery from 82% to 45% (Xu, Sep 2026)
- **Cost:** mixed, small: error text and full traces add tokens unless capped (Carlini, Feb 2026); masking old observations, errors included, cut cost per instance by more than half in most configurations against the full history (Lindenbauer, Aug 2025); fresh starts used similar or fewer tokens, e.g. 108,289 to about 89,000 (Adnan, Jun 2025); filtering 949 error messages with a prompt cost $0.09 (Xu, Sep 2026); contract notes raised list cost 7% with no extra model call, against 498% for a reviewer loop (Panthi, Aug 2026); a new-turn note recomputed a median 1,081 prompt tokens at the failed step against 965 for rewriting the history (Woo, Nov 2026)
- **Security:** mixed, small: showing third-party error text opens an injection channel, which approval gates closed in one study: in one small red-team study an exfiltration instruction inside a tool error was followed by two of four frontier models as written and by all four after one round of rewording, against one of four when the same instruction sat in a successful result, while Gemini CLI and Codex with approval gates blocked every payload (Patel, Jun 2026); a harness note that restates tool text in a user turn gives it more authority, untested (Woo, Nov 2026)
- **Governance:** improves, small (unmeasured)
- **Brand:** improves, medium: a model almost never misreported a failure its tool returned as status:error (at most 1.2% dishonest answers), but asserted or relayed a value, or invented a refusal reason, in 3.5% to 45.3% of failures returned as status:ok, by failure type under a deployment prompt (Sethi, Sep 2026); a coding agent given a failure note reported a forbidden data service in 12 of 12 runs and wrote no fabricated result file, against fabricated files in 33% and 50% of runs without it (Woo, Nov 2026)

## Caveats

Two harness ablations now separate showing a failure from hiding it, both on open-weight models: across 13 models (3B-70B), deleting the failed exchange did 1.9-3.8 points worse than keeping it and, when the note replaced it in the user message, broke stopping in Llama models, and on four current models a contract note on silently failed results raised completion from 10.9% to 28.1%, with no net gain where most runs succeeded anyway and as many harms as rescues on clean runs; no ablation covers a closed frontier model, and the honesty result (at most 1.2% dishonest answers on status:error, up to 45.3% on status:ok) rests on one 2025 model with a same-family judge. Failures that accumulate hurt: in 135M-1.7B models the verbatim failed call raised repeats (though deleting it was worse), wrong answers in a model's own history lowered its later accuracy in non-thinking models (not fixed by scale, absent in one thinking family), and on HumanEval restarting fresh after 2-3 failed fixes beat continuing for all six models tested. What the error says matters as much as whether it is shown: naming the next step or the recovery tools carried the measured gains while more diagnostic detail did not measurably help, a step the agent cannot take cut recovery from 82% to 45%, and for failures in the agent's own call the wording barely mattered. Third-party error text is also an injection channel: in one small red-team study frontier models followed instructions planted in tool errors through raw APIs, though two coding CLIs with approval gates blocked them.
