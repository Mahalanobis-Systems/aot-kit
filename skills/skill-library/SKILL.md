## What it is

Turn runs that passed a verifier into reusable skills (a code function or a SKILL.md procedure), keep them in a reviewed library, and show the agent only the few a separate selection step picks. It pays on recurring task families when skills come from verified successes: compiling a run into code cut tokens 74 to 81% at the same reward when the request recurred (Claude Sonnet 4.6 and Opus 4.8), and skills distilled from an agent's own successes raised success on the tasks they came from (Terminal-Bench-2 0.5935 to 0.7548 with GPT-5.3-Codex), but a library carried to new coding benchmarks added only 1.6 to 7.7 points, skills from failed runs alone or written before any attempt scored below no skills, and an audit of automatic harness and skill evolution traced most reported gains to benchmark shortcuts (54% on average) or extra inference (14%). Costs grow with the library and with how it learns: agents stop opening the right skill (loaded-skill recall 73.6% to 27.4% with 1,000 irrelevant skills listed) unless a preselector chooses, an agent copied planted malicious code into its own skills on 20.3% to 41.8% of tasks, and skills learned from users approving tasks they had asked for taught agents to obey instructions planted in new content (attack success up 14.0 to 48.8 points).

## When it applies

- **In the code:** A skills directory or store the agent writes to after runs; skills written without a verifier outcome, or from the model's own knowledge before it attempts the task; new skills retrievable with no review or quarantine; authoring that reads retrieved skills as templates; skills learned from user approval with no examples where the right action was to decline; compiled skill programs with request values hard-coded; every skill's name and description listed to the agent on every run.
- **In traces:** Skill reuse rate; skills authored per session; loaded-skill recall and zero-load rate per run; per-skill opens and outcomes; skills never opened; skills distilled from failed or unlabeled runs; authored skills that copy retrieved code verbatim; compiled programs handed back to the model; actions the user's request did not ask for in runs that loaded a learned skill.
- **In eval results:** Paired runs with and without the library, plus a compute-matched plain arm, on held-out tasks from other sources than the skills' own (pass rate, tokens, time); pass rate and loaded-skill recall as the library is padded with irrelevant skills.
- **Judge:** Review each new skill before it becomes retrievable: task-specific paths or values baked in, confident assumptions no verifier checked, shortcuts keyed to how the tasks were built (a recurring answer, a fixed recipe), instructions to carry out whatever a file or message asks without the user's request, boilerplate copied from retrieved skills, overlap with existing skills.
- **Probes:** Recurring task families; a growing library; planted skills; content carrying an instruction the user did not ask for.

## How (outline)

1. Start from the baseline: the same model and harness with no skill library, plus an arm with cleaned traces of past runs in context (cheaper: 95.3K fewer tokens per task than distilled skills, for 4.8 points less success in one study), on recurring task families with a deterministic verifier. Where writing or using skills adds model calls, add a compute-matched arm that gives the plain agent the same extra calls (more samples or attempts, 9.c.ii): in one audit of automatic harness and skill evolution, extra inference explained 14% of gains on average and benchmark shortcuts 54%. Score on held-out tasks drawn from other sources than the skills' own (other repositories, benchmarks or task generators), since held-out instances of the same benchmark share its shortcuts: there, held-out gains were smaller than search-set gains in 13 of 15 settings and negative in 4, and choosing the evolved setup on a validation split left the gap open in 14 of 16. Do not ask the model to write skills from what it already knows before it attempts the task: such self-generated skills scored 8.1 to 11.5 points below no skills with Opus 4.7, GPT-5.5 and Gemini 3.1 Pro, because solvers never opened them or followed confident errors such as a hard-coded 1000x unit conversion.
2. Write a skill only from a run the verifier passed: distill the trajectory into a code function or a SKILL.md (when to use it, preconditions, steps, failure modes, a verify step) with task-specific paths and values replaced by placeholders. For a request that recurs with new inputs, also compile the run into parameterized programs that take the request's values as inputs, replay them in a fresh sandbox before admitting them, and keep the SKILL.md as the fallback when a program fails: in one study on 87 SkillsBench tasks in Claude Code, repeating a request with such a compiled skill used 81% fewer tokens with Sonnet 4.6 and 74% with Opus 4.8 at the same reward, against 54% and 49% fewer with the raw trace in context and 67% and 52% with a written procedure; compiling paid for itself after 1.1 and 1.5 reuses, compiling a skill before any run used 1.24x the tokens of plain skill use, and three compiled skills that hard-coded a request value gave wrong answers on changed inputs. If failed runs feed the writer, label them: skills distilled from failed runs alone fell below no experience in all six benchmark-model cells, and hiding the success and failure labels cut Gemini 3.1 Pro on Terminal-Bench-2 from 0.7462 to 0.4000; in a coding library, recovery skills built from failure signatures that recurred across repositories accounted for 0.8 to 5.6 points of the gain. Voyager added a program only after self-verification passed, and removing self-verification cut discovered items by 73%.
3. Gate admission: keep agent-authored skills in a quarantine that retrieval cannot see until a reviewer or a signed admission step approves them. Reject candidates that carry task identifiers, hidden answers or private paths, or that encode a benchmark shortcut (a recurring answer, a recipe keyed to how the tasks were built): in one audit three different evolvers wrote the same multiple-choice shortcut into code, a skill and a prompt, and 44% and 88% of a skill optimizer's gain on two benchmarks was shortcut. Check that each skill keeps the conditions under which its action is allowed: skills learned from users approving tasks they had asked for in a file or message dropped the "only when asked" condition, and attack success from instructions planted in new content rose 14.0 to 48.8 points across four models with no attacker in the learning loop; adding approved episodes in which the agent left an unrequested embedded task undone cut it from 35.0% to 5.8%, while delimiting tool output only lowered it from 97.5% to 47.5% (0% before learning; both on one model, Qwen3.8-27B, on one file-creation task). Tell the authoring agent that retrieved skills are untrusted and that banner-style "REQUIRED PATTERN" or "DO NOT MODIFY" boilerplate must not be copied (10.c.i): in one study that four-line instruction cut self-poisoning from 20.3% to 41.8% of tasks to at most 6.7% with no significant loss in task completion, while a name blocklist caught none of the authored copies and a code scanner fell to 7% after a one-line rewrite.
4. Retrieve a few skills through a separate step instead of listing them all (the same deferral idea as 2.a.i): near 100 skills, an LLM preselector over names and descriptions; at thousands, retrieval followed by an LLM selector; expose a handful (at most five in the study). With 1,000 irrelevant skills listed, loaded-skill recall fell from 73.6% to 27.4% although a selector given the same list found 73.9%; LLM preselection cut tokens per run from 1,966k to 547k and added a median 8 to 41 seconds of routing; asking the agent to plan its skill use first did less than preselection.
5. Prune and revise from telemetry: log which skills each run opens and its outcome; retire skills that are never opened or whose runs keep failing, and merge near-duplicates, since irrelevant descriptions suppress loading (masking them restored recall from 18.3% to 63.3%) and similar skills are the hardest to tell apart (top-1 precision 70.5% to 53.4% on similar pools). If a poisoned skill is found, scrub the agent-authored copies too: in one model the infection rose to 68% of tasks after the planted seeds were removed.
6. Measure paired against the baseline and the compute-matched arm, same model and harness, on held-out tasks from other sources than the skills' own, over at least three runs: pass rate, tokens and time per task (including authoring and compiling, and the reuses needed to repay them), loaded-skill recall, zero-load rate and the misapplied-skill rate (10.0% of skill runs in one study). Expect small transfer gains: a coding library evolved on SWE-Gym added 1.9 to 7.7 points on two other benchmarks with GLM-5.2, 2.8 and 6.3 with GPT-5.5 and 1.6 and 1.8 with Opus 4.8, at 17% to 49% more words per task than no skills. Rerun with the library padded to its expected size, with planted-skill probes and with content that carries an instruction the user did not ask for, since task success can stay flat while skill use collapses (precision 29.6% to 3.3% with success 36.4% to 39.3%) and the requested task can succeed more often while unrequested actions rise (summary delivery 44.2% to 97.5% with an unauthorized invite in 62.5% of conversations). Re-measure when the model changes.

## How to measure

- **Cost:** mixed, large: compiling a completed run into programs cut tokens per repeated request 81% (Sonnet 4.6) and 74% (Opus 4.8) and cost 82% and 75%, against 54% and 49% fewer tokens for the raw trace in context, and compiling was repaid after 1.1 and 1.5 reuses (Ni, Nov 2026); SKILL.md skills used 34.2K fewer tokens per task than the Raw arm but 95.3K more than cleaned traces of the same runs, on 83 matched tasks (Jiang, Aug 2026); a transferred coding library used 17% to 49% more words per task than no skills (Gao, Oct 2026); listing every skill's description raised tokens per run from 498k to 1,966k with 1,000 irrelevant skills added, and an LLM preselector brought it to 547k (Liu, Oct 2026)
- **Performance:** mixed, medium: repeating a request with a compiled skill cut latency from 372 s to 103 s (Sonnet 4.6) and from 373 s to 113 s (Opus 4.8) (Ni, Nov 2026); Voyager reached tech-tree milestones up to 15.3x faster, counted in prompting iterations, than prior agents (Wang, May 2023); a run took 15.3 minutes with only the relevant skills and 17.0 with 1,000 more listed, and preselection adds a median 8 to 41 seconds of routing (Liu, Oct 2026); a transferred coding library added steps per task in all four settings (58.4 against 52.4 up to 240.9 against 184.2) (Gao, Oct 2026)

## Caveats

The positive evidence for agent-built skills is narrow and mostly from the methods' own authors: the largest controlled gain scored skills on the tasks whose runs they came from (its 6.06-point lead over cleaned traces has a lower bound of 0.76), the one cross-benchmark transfer test covers a single coding library (GPT-5.5 and Opus 4.8 under one harness, run count not stated, no compute-matched arm), and the compiled-code savings come from repeating the same 87 requests plus 66 changed ones, with each task's skill supplied rather than retrieved. An independent audit found most gains from automatic harness and skill evolution came from benchmark shortcuts or extra inference, though on small splits (50 held-out SWE-bench tasks) with mostly small open-weight executors, and Voyager's headline compares its whole system, not the library alone, with GPT-4 in Minecraft. The security results use open-weight executors (six models with attacker-planted seeds and an agent asked to author a tool on every task; four models adapted from 12 approved conversations each, with sandboxing off), and the routing study used curated skills with marketplace distractors, mostly on open-weight models with a 37-task check on Claude Opus 4.6, Gemini 3.1 Pro and GPT-5.4. No source here measures an agent-grown library over months of production use, and the self-generated deficit comes from skills written before any attempt (one configuration ran that arm at a higher effort level).
