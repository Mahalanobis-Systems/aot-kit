## What it is

Make the search tool show the agent enough to choose what to open, give it a reader that keeps the pages it opens, and have the tool say plainly when it found nothing. Return per result its source metadata and the part that matches the query (not the page's opening), five or more results, and a short reference in place of a snippet already shown; retry failed searches and reformulate thin ones; expose metadata filters; let a model that can run code filter results before they enter its context; and drop sources that leak the answer, are untrustworthy or can be edited by anyone. Expanding one question into many queries up front has not helped. In single studies, query-matched snippets with repeats suppressed reached 94.94% on BrowseComp-Plus with GPT-5.4 against 84.70% for passage openings (3,365 against 26,316 tokens per search, though with more searches), filtering results in code raised BrowseComp from 45.3% to 61.6% for Claude Opus 4.6 (the vendor's own test), a reader that saves fetched pages beat snippets alone by 8.5 to 17 points, and a plain "no reliable results" message raised abstention on unanswerable questions from 23% to 97% for two Qwen3 models. The limits: most gains come from the method's authors or vendor, Claude Sonnet 5.5 and Opus 5.5 ignored the no-result message, 13 words planted on one often-retrieved Reddit page turned up in 38% to 51% of the reports that saw it, and the effects of result count and retries are unmeasured.

## When it applies

- **In the code:** a search tool returning titles or URLs only; snippets cut from the start of each result rather than the part matching the query; a fixed small result count; no page reader beside search, or a reader that injects one fixed reading of the page that cannot be queried again; a tool that always returns its top-k even when nothing matches; no retry; no filter parameters over a corpus with metadata; results passed to the model unfiltered, including from hosts of eval datasets and from pages anyone can edit
- **In traces:** many page fetches per question, or the same page fetched again; the same snippet returned in several searches; queries returning zero or irrelevant results followed by the same query, by giving up or by an answer anyway; near-identical consecutive queries; answers given without opening any result, or wrong answers whose answer text was visible in a returned snippet or page; results from the wrong product, version or date; one forum or wiki page cited across many unrelated questions; results from dataset hosts or pages containing the eval question or the eval's name; failure rows labeled missed-read
- **In eval results:** retrieval recall below what answer accuracy needs; failures where the answer was in an unfetched result; wrong rather than unknown answers on questions the corpus cannot answer
- **Probes:** Questions whose answer-bearing documents have been removed from the index, and, for evals with web search, questions whose answers are published online.

## How (outline)

1. Start from the search tool as it is: from traces, count per question the searches, page opens, near-identical repeated queries, and searches that returned nothing useful together with what followed (the same query, a reformulation, giving up, or an answer anyway); count answers given without opening any result and wrong answers whose answer text was visible in a returned snippet or page (53 to 57 of 100 questions in one comparison of three search APIs, by string match); measure the tokens each search call returns and the tokens search results take per question; and count the results and citations that come from pages anyone can edit (forums, wikis, video pages).
2. Return results the agent can choose from: a title, URL, source and date metadata and a snippet per result, not just titles or URLs, and enough results to choose among (VeRO's stronger agent used five or more results with retries, its weaker one three without; no study here isolates the count). Make each snippet the part of the result that matches the query, not its opening lines, and replace a snippet the agent has already seen with a short reference to it: in one harness comparison on BrowseComp-Plus with GPT-5.4, ten reranked passages per query, each shown as its best-matching segment with repeats replaced, reached 94.94% against 91.45% for 180-character query-biased snippets and 84.70% for 512-token passage openings, returning 3,365 tokens per search against 3,690 and 26,316 but searching more (16.8 searches per question against 12.1 and 4.5); with search as the only tool, adding reranking and per-passage snippet selection to plain dense retrieval raised one open model from 62.61% to 70.84%. Snippet size trades page opens for tokens: under the same agent, the search API with the richest snippets (a median 7,810 tokens of results per question, against 2,704 for the leanest) showed answer-bearing snippets on 30 of 100 questions against 16 and opened pages on 65% of questions against 81%, at the same accuracy; in VeRO, adding snippets raised SimpleQA training accuracy but not validation.
3. Put a page reader beside search, and keep what it fetches: a fetch tool that saves the full page to a per-question workspace and returns only its path and size, with grep and bounded line reads across every saved page, beat a snippets-only agent (BrowseComp 44.5, 52.5 and 70.5% against 27.5, 37.5 and 62.0% on three models), a visit tool returning a goal-focused summary made at fetch time (37.5, 48.0 and 64.0%) and a one-page-at-a-time browser (42.0, 50.5 and 66.0%), and it searched less than the snippets-only agent (58 to 67 searches per question against 70 to 101); confining grep to one page at a time cost 5 points on one model. A lighter form is a read tool that expands the text around a result the agent already has instead of running a new search (in the snippet harness above, this with repeat suppression added 9.28 points, 70.84% to 80.12%, on one open model). Where the model can run code, let it filter search and fetch results in code before they enter its context: Anthropic reports BrowseComp rising from 33.3% to 46.6% for Claude Sonnet 4.6 and from 45.3% to 61.6% for Opus 4.6, and DeepSearchQA F1 from 52.6 to 59.4 and 69.8 to 77.3, with 24% fewer input tokens on average, but price-weighted tokens rose for Opus 4.6 (the vendor's own test of its own tool). If you keep a visit tool that returns one reading of the page, a summary beat a goal-focused chunk on every model. How much of a page each read returns is 2.c.i.
4. Make a failed search visible: when nothing reliable matches, return a short message instead of the usual top-k irrelevant passages, saying so and what to do next (for example "No reliable results were found for this query. The index may not contain the information needed.", then try a different query or answer unknown). In one study this raised abstention on unanswerable questions from 23% to 97% for Qwen3-8B and Qwen3-32B and from 28% to 57% for Claude Haiku 4.5 (80.7% with the "what to do next" sentence), cutting wrong answers almost one for one, while a warning placed above the usual passages barely helped. Claude Sonnet 5.5 and Opus 5.5 ignored the message and answered from memory but followed a system-prompt instruction to answer unknown without evidence (abstention +16 points), so state it in the system prompt too. The tool needs a miss detector: a score-based one held to 5% false refusals delivered only part of the gain, and every false refusal on an answerable question costs that answer.
5. Retry a search that errored (transient failures, per 2.b.i), and when a query returns little, reformulate rather than repeat it: prompt the agent to start with short, broad queries and then narrow (Anthropic's research agents defaulted to overly long, specific queries that returned few results; unmeasured), and let it write its own targeted queries in the corpus's terms (removing an agent-written schema-retrieval action cost 6.7 to 7.6 points of schema recall in one study; large schemas are 8.b.ii). Do not expand the question into many queries up front: a query planner lowered recall, and its sub-tasks used as query expansion did not raise table recall (gpt-4o).
6. Filter sources: expose the corpus's metadata (date, domain, product, version, source) as filter parameters, and drop results from untrustworthy sources or sources that leak the answer (source filtering gained 3.3% on FACTS in VeRO). Treat pages anyone can edit as untrusted: in one study of open deep-research agents (GPT-4o-mini), 13 words appended to the search snippet of one often-retrieved Reddit page reached the agent in 57% to 76% of runs and were mentioned in 38% to 51% of the reports where they were seen; blocking eight such domains at the search tool removed the exposure at a small measured cost (14.9 to 12.9 citations per report, rubric score 4.30 to 4.26) but drops genuine community content and misses other writable sites, perplexity filters failed because the planted text was more fluent than real posts, and an LLM screen of each forum result would add 7% to 11% more model calls (33% to 61% for every result). Injection defenses in general are 10.c.i. In evals with web search, block hosts of the eval's own data and drop retrieved text that contains the eval's name or questions: search agents found HLE, SimpleQA and GPQA items with their answers on HuggingFace for 0.99% to 4.15% of questions, and blocking HuggingFace cut accuracy on those questions by about 15%; in Anthropic's BrowseComp run, Claude Opus 4.6 took 11 of 1,266 answers from benchmark materials (two by identifying the benchmark and decrypting its answer key), got around URL blocklists, and blocking any result that mentioned "BrowseComp" worked best (re-run with a blocklist, 8 of the 11 were solved legitimately, 86.81% to 86.57%).
7. Change one thing at a time and run paired evals on the same questions and model, scoring answer accuracy, whether an answer-bearing result was returned, opened and used, searches and page opens per question, tokens returned per search and per question, price-weighted cost, and wrong rather than unknown answers on questions the corpus cannot answer; when comparing search APIs, compare solved questions one by one, since three providers at 25 to 26 of 100 solved different questions (44 of 100 solved by at least one).

## How to measure

- **experiment** (Tier 3): paired runs on the same questions and model, the current search tool against one change at a time (a snippet and metadata per result, the best-matching segment of each result instead of its opening, suppression of repeated snippets, result count, a page reader that keeps fetched pages, code filtering of results where the model can run code, an explicit no-result message, retries and reformulation prompts, source filters including a block on pages anyone can edit); report answer accuracy, whether an answer-bearing result was returned, opened and used, searches and page opens per question, tokens returned per search and per question, price-weighted cost, and abstention against wrong answers on questions whose documents were removed from the index; when comparing search APIs, compare solved questions one by one, not only accuracy; for a source filter, plant a short promotional passage in one often-retrieved forum page and count the runs and reports it reaches with and without the filter
- **monitor**: in production traces: searches returning nothing useful and what followed (the same query, a reformulation, giving up or answering anyway); near-identical consecutive queries; answers given without opening any result; tokens returned per search and per question; snippets returned again in later searches; pages fetched more than once; results from the wrong product, version or date; the share of results and citations from pages anyone can edit, and single such pages cited across many questions; false refusals if the tool can refuse; in evals with web search, results from hosts of the eval's data and retrieved text that contains the eval's name or questions

## Expected impact

- **Quality:** mixed, medium: what each result shows and how pages are read: reranked per-result snippets with repeats suppressed reached BrowseComp-Plus 94.94% with GPT-5.4 against 91.45% and 84.70% for two open harnesses, and reranking with per-passage snippet selection added 8.23 points over plain dense retrieval on one open model (Vuong, Nov 2026); code filtering of search and fetch results lifted BrowseComp from 33.3% to 46.6% (Claude Sonnet 4.6) and 45.3% to 61.6% (Opus 4.6) (Anthropic, Feb 2026, vendor); a reader that keeps fetched pages queryable: BrowseComp 44.5, 52.5 and 70.5% against 27.5, 37.5 and 62.0% with snippets only (Liu, Aug 2026); a no-result message cut wrong answers on unanswerable questions from 64.5% to 10.5% for three models that obeyed it, but moved Sonnet 5.5 and Opus 5.5 abstention only from 1.4% to 3.2% (Chandradevan, Oct 2026); three search APIs: 25, 25 and 26 of 100 correct (Selvam, Jul 2026); snippets: SimpleQA train +0.15 but validation -0.06; source filtering +3.3% on FACTS (VeRO, Feb 2026); up-front query expansion: no gain (Chen, Jul 2025); blocking forum domains: rubric 4.30 to 4.26 (Zhang, May 2026); retries and result count unmeasured
- **Cost:** mixed, small: per-result snippets returned 3,365 tokens per search against 26,316 for 512-token passage openings (GPT-5.4) but meant more searches (16.8 against 4.5 per question), with no total cost reported (Vuong, Nov 2026); code filtering used 24% fewer input tokens on average, but price-weighted tokens rose for Opus 4.6 while falling for Sonnet 4.6 (Anthropic, Feb 2026, vendor); a page reader cut searches per BrowseComp question (70 to 101 with snippets only, 58 to 67 with a workspace reader) but adds fetch, grep and read calls (Liu, Aug 2026); richer snippets meant fewer page opens (65% of questions against 81%) for more result text (a median 7,810 against 2,704 tokens per question), with no significant difference in total tokens (Selvam, Jul 2026); a no-result message left searches mostly unchanged but tripled them for one model on one dataset (1.38 to 4.12 per question) (Chandradevan, Oct 2026); an LLM screen of forum results would add 7% to 11% more model calls (Zhang, May 2026)

## Caveats

Each design result comes from one study, most by the method's authors or vendor: the per-result snippet harness (one run per question on closed corpora) bundles reranking, snippet selection, a different reader and deduplication, and its one isolating ablation is a single open model; the code-filtering gains are Anthropic's test of its own tool with no run counts and higher price-weighted cost for Opus 4.6; the workspace reader reports the best of three runs on 200 BrowseComp questions; and the no-result message used an oracle trigger on 557 Wikipedia questions, where a realistic detector recovered only part of the gain. The strongest models respond differently: Claude Sonnet 5.5 and Opus 5.5 ignored a refusal in the tool result but followed a system-prompt instruction (+16 points of abstention), and in VeRO snippets helped on SimpleQA's training split but not validation. Result count and retries rest only on VeRO's description of a stronger agent (five or more results with retries, against three without, alongside other differences), the one search-API comparison is 100 questions with one model and one run per provider, and latency is unmeasured. The poisoning and blocklist result is on open deep-research agents running GPT-4o-mini, where the blocklist worked by dropping all forum content and quality was scored by an insensitive rubric; the contamination results are Perplexity's Sonar agents and one Anthropic run of Opus 4.6; and up-front query expansion was tested only on table retrieval with gpt-4o.
